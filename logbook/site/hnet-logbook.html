EXP-000 · Cartesia Fig. 7 re-analysis

2026-10-28 · status: done · cost: $0 · script: logbook/exp000_reference.py

Question. How much of the blog's ">10x fewer tokens" comes from the architecture, and how much from comparing a cooled-down H-Net with a stable-phase SmolLM3?

Data. The per-checkpoint scores behind blog I Fig. 7, extracted from the page's chart bundle into configs/reference/blog1_fig7_{hnet,smollm3}.csv: * the H-Net has 154 points to 0.99T tokens (cooldown from 0.855T); * SmolLM3 has 117 points to 11.04T (stage 1 up to 7.93T).

The six tasks are HellaSwag, ARC, PIQA, WinoGrande, CSQA and MMLU.

Method. Fit SmolLM3's stage-1 (stable-LR) average as a quadratic in log tokens. For each stable-phase H-Net point, find the SmolLM3 token count that reaches the same score.

Results.

H-Net tokens H-Net avg SmolLM3 avg at same tokens SmolLM3 tokens to match (smoothed) Data multiplier
94B 55.66 53.87 162B 1.7x
189B 58.11 56.86 560B 3.0x
301B 58.74 — 822B 2.7x
0.99T (after cooldown) 63.82 — 11.04T (SmolLM3 final, after stages 2–3) 11x

Takeaways. * The architecture effect at matched stable phase is real but ~2–3x, not 10x. The H-Net's cooldown adds ~2.3 points (61.5 → 63.8). * Our pass criteria for any H-Net vs baseline comparison use stable-vs-stable multipliers. Cooldown is a separate, explicitly labelled branch. * Cartesia's SmolLM3 Winogrande (63.69 at the end) differs from the model card (58.88), so their eval setup differs from the card. Our harness is validated against these CSV numbers, not the card.

EXP-001 · What the blog's chunk-viewer data says about the improved router

2026-10-28 · status: done · cost: $0 · scripts: scripts/reference/parse_chunk_viewer.py, scripts/reference/analyze_chunk_viewer.py, logbook/exp001_chunk_viewer.py

Question. The blog's H-Net is unreleased and differs from the paper's (which the blog calls "LH-Net", lazy/lookahead). What does its router actually do?

Data. Blog I Figs. 10–11 are interactive viewers. Their data files hold 96 texts (45 natural-language, 51 code) with, for each text: * the improved H-Net's stage-0/1 boundary positions and per-byte boundary probabilities p; * LH-Net's boundaries on the same texts; * Llama-3 and in-corpus BPE tokenizations.

These were parsed as data (no page code was executed) into configs/reference/chunk_viewer.json. The viewer code labels an improved-H-Net boundary byte "ends here" (ends: true on every example) and a trailing chunk without one "unfinished".

Results. * End-of-chunk boundaries. p ≥ 0.5 coincides with "this byte is the last byte of a stage-0 chunk" on 99.76% of 327,081 bytes. The decision at byte t can only use bytes ≤ t, so there is no lookahead. * Spaces go at the end of chunks. 92% (English), 78% (other languages) and 68% (code) of stage-1 chunks end right after a space. LH-Net and BPE attach the space to the next word instead (≤ 20%). * Clean stage-1 units.

Stage-1 cuts English Other languages CJK
Inside a word: improved H-Net 0% 0.5% —
Inside a word: LH-Net 3% 3% —
Inside a UTF-8 character: improved H-Net 0% 0.01% 0.5%
Inside a UTF-8 character: LH-Net 3% 24% 81%

This confirms the blog's CJK claim quantitatively. * Compression (bytes per stage-1 chunk):

What we implement from this. * Routers declare start or end boundary semantics. * With end semantics, the chunk vector is the last byte's state, and byte t reads the most recent chunk that ended at or before t. * The router function is still a guess. Candidates end_linear, end_mlp and end_cosine_shift go through the 1–10M architecture search (PLAN §2b), with the chunk statistics above as the targets for our trained models.
